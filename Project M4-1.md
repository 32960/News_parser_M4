# AINEWS: AI-генератор постов для Telegram 

## 1. **Введение**

Вас взяли работать в стартап, который хочет автоматизировать новостной Telegram-канал на новом уровне.
 Ваша задача — сделать сервис, который не просто парсит новости, но использует ИИ для генерации ярких, лаконичных и интересных постов на основе собранных материалов.
 Сбор новостей и публикация должны выполняться по отдельным расписаниям: сбор — каждые 30 минут, автоматическая публикация — по одному готовому посту из очереди в начале и середине каждого часа (UTC). Управление сервисом и мониторинг доступны через API.

Вам предстоит интегрировать несколько сервисов: парсинг новостей (сайты и Telegram-каналы), очередь задач, генерацию постов с помощью AI (например, OpenAI GPT-4), публикацию через Telethon и реализацию панели управления источниками.

Срок выполнения — **2 недели**. 4 вебинара. 



## 2. **Функциональные блоки**

### **1. Сбор и парсинг новостей (сайты и Telegram-каналы)**

- Собирать новости не только с сайтов, но и из публичных Telegram-каналов через Telethon, используя тот же пользовательский аккаунт, что и для публикации.
- Для каждого поддерживаемого сайта реализовать отдельный парсер. В коде определить соответствие между поддерживаемыми адресами источников и парсерами; парсер выбирать по домену и, при необходимости, пути URL. Поддержка нового сайта добавляется изменением кода.
- Для всех публичных Telegram-каналов использовать общий парсер Telethon. Подключение нового доступного аккаунту канала выполняется через API по публичному username или ссылке `https://t.me/<username>` и не требует изменения кода.
- По расписанию запускать сбор новостей только из источников с `enabled=true` (каждые 30 минут, Celery Beat).
- Предусмотреть ручной запуск того же сбора через `POST /api/parse/`: API ставит задачу в Celery, которая запускает сбор из всех включённых источников. Новые новости проходят обычную цепочку подготовки постов; публикация выполняется по установленному расписанию.
- Каждая новость должна содержать `title`, `raw_text`, `source_id`, `collected_at`. Для новости с сайта обязателен `url`, для Telegram — `telegram_channel_id` и `message_id`; `summary` и `published_at` могут быть `null`. Правила заполнения приведены в модели `NewsItem`.
- Для сайтов сохранять извлечённый текст новости без HTML-разметки; для Telegram — текст сообщения или подпись к медиа. Материалы без непустого текста пропускать.
- Новости с сайтов, для которых не удалось получить абсолютный URL статьи, пропускать.

------

### **2. Очередь задач и асинхронная обработка**

- Использование **Celery** и брокера (**RabbitMQ** или Redis) для обработки задач (парсинг, генерация, публикация).
- Фоновая цепочка подготовки: сбор из включённых источников → исключение дублей → генерация поста через AI → сохранение готового поста в очереди на публикацию.
- Публикация — отдельная периодическая задача Celery, которую Celery Beat запускает независимо от сбора и генерации. Очередь на публикацию формируется из записей `Post` со статусом `generated` в общей БД.
- Все тяжелые операции — в отдельных тасках Celery.
- Задачи чтения Telegram и публикации выполнять последовательно: одновременно файл пользовательской сессии может использовать только один клиент Telethon. Остальные задачи могут выполняться параллельно.

------

### **3. AI-генерация постов**

- Использовать OpenAI GPT-4 или другую AI-модель через публичный API.
- Для генерации по сохранённой новости передавать модели непустую `summary`, если её предоставил источник, иначе — `raw_text`. На выходе получать сгенерированный пост по заданному промпту.
- Генерация по сохранённой новости допускается после проверки дублей и при `Source.enabled=true`. Перед вызовом AI API проверять актуальное значение `enabled`; если источник отключён, завершать задачу без вызова AI API. Повторное обнаружение уже сохранённой новости при сборе не должно запускать новую генерацию.
- Настроить промпт: "Сделай краткое, интересное описание новости для Telegram-канала, добавь emoji, call to action".
- Обработка ошибок API (rate limit, недоступность).
- До первой попытки генерации создавать `Post` со статусом `new`; `generated_text`, `generated_at` и `published_at` имеют значение `null`. При успешной генерации сохранять непустой `generated_text`, время `generated_at` и статус `generated`. При ошибке генерации устанавливать `generation_failed`.
- Ручная генерация запускается через `POST /api/generate/` по `news_id`: API создаёт `Post` со статусом `new`, ставит задачу в Celery и возвращает `post_id`. После успешной генерации пост попадает в общую очередь публикации; результат доступен через `GET /api/posts/{id}/`.

------

### **4. Отбор источников и исключение дублей**

- Отбор выполняется по флагу `Source.enabled`: новые задачи сбора и генерации обрабатывают только включённые источники.
- Отключение источника сохраняет его новости и посты. Уже сгенерированные посты остаются в очереди и публикуются по расписанию.

**Правила исключения дублей:**
Н
- При сборе проверять совпадения по всей сохранённой истории перед созданием новой записи и запуском AI-генерации.
- Для сайтов дублем считать точное совпадение строк абсолютного `url` статьи, включая параметры запроса.
- Для Telegram дублем считать совпадение пары `telegram_channel_id` + `telegram_message_id`. Использовать числовой ID канала; одинаковые `telegram_message_id` в разных каналах относятся к разным сообщениям.
- Если новость уже сохранена, пропускать её: не создавать новую запись и не запускать повторную генерацию. Сохранять первую собранную версию; изменения текста по тому же URL или для той же пары Telegram ID не создают новый пост.
- Материалы с разными URL либо разными парами Telegram ID считать разными новостями, в том числе при одинаковом тексте.
- Обеспечить в БД уникальность `url` для новостей с сайтов и пары `telegram_channel_id` + `telegram_message_id` для новостей из Telegram. При одновременном обнаружении одного материала несколькими задачами сохраняется одна запись. Эти проверки должны работать и после перезапуска сервиса.

------

### **5. Публикация в Telegram через Telethon**

**Общая настройка Telegram для сбора и публикации:**

- Использовать один пользовательский аккаунт Telegram и одну сохранённую сессию Telethon для чтения источников и публикации. Аккаунт должен иметь доступ к каналам-источникам и быть администратором целевого канала с правом публикации сообщений.
- Первоначальную авторизацию выполнять отдельной командой `python -m app.telegram.authorize` до запуска фоновых задач: ввод номера телефона, кода подтверждения и, если включена двухфакторная аутентификация, пароля. Сессию сохранять для последующих запусков.
- При обычном запуске использовать сохранённую сессию. Если она отсутствует или авторизация недействительна, завершать Telegram-задачу с понятной ошибкой, без интерактивного запроса кода или пароля в Celery worker.
- Настройки передавать через переменные окружения: `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_SESSION_PATH` (путь к файлу сессии), `TELEGRAM_TARGET_CHANNEL` (username или ID целевого канала).
- В репозиторий включать `.env.example` с названиями настроек и пустыми значениями секретов. Локальный `.env` и файл сессии с его служебными файлами исключить из Git через `.gitignore`.

**Публикация:**

- После успешной генерации сохранять пост со статусом `generated` и временем готовности `generated_at` для последующей публикации.
- Автоматическую публикацию запускать через Celery Beat в `HH:00` и `HH:30` каждого часа, круглосуточно. Часовой пояс расписания — UTC.
- Каждый запуск выбирает один готовый пост со статусом `generated`, доступный на момент выбора, и отправляет его в указанный Telegram-канал через Telethon. Порядок выбора: по возрастанию `generated_at`, при одинаковом времени — по `id`.
- Если готовых постов нет, завершать запуск без отправки сообщения.
- Перед отправкой проверять сохранённый статус `Post`: если он равен `published`, завершать задачу без повторной отправки.
- Для учебной версии достаточно проверки сохранённого статуса. Известное ограничение: если сервис завершится после фактической отправки, но до сохранения результата в БД, повторная попытка может создать дубль в канале. Устранение этого ограничения не входит в обязательную часть проекта.
- После успешной отправки устанавливать статус `published`, сохранять фактическое время публикации в `published_at`.
- При ошибке отправки устанавливать статус `publication_failed`; `generated_text` и `generated_at` сохранять, `published_at` оставлять равным `null`. При повторной отправке использовать уже сгенерированный текст.
- Логировать успешные публикации и ошибки.
- Ручную публикацию выполнять через `POST /api/posts/{id}/publish/`: отправка готового поста запускается задачей Celery вне расписания. Допустимы статусы `generated` и `publication_failed`; для `published` возвращать сохранённый результат без отправки, для `new` и `generation_failed` возвращать HTTP 409.

### **6. Управление сервисом через API**

- REST API для добавления, редактирования, удаления источников новостей (сайты, Telegram-каналы).
- Физически удалять источник разрешено только при отсутствии связанных `NewsItem`. Если новости уже сохранены, возвращать HTTP 409 с описанием причины отказа и возможностью отключить источник через `enabled=false`. Отключение прекращает новые задачи сбора и генерации для источника, сохраняя сам источник, его новости и посты; готовые посты остаются в очереди на публикацию.
- Для источников типа `site` API позволяет подключать и настраивать только адреса, поддерживаемые реализованными парсерами. При добавлении или изменении адреса проверять наличие подходящего парсера; для неподдерживаемого адреса возвращать HTTP 422 с понятным описанием ошибки, не создавая и не изменяя источник.
- Для источников типа `telegram` API позволяет подключать публичные Telegram-каналы к общему парсеру по username или ссылке `https://t.me/<username>`.
- Включение и отключение источника выполнять через изменение поля `enabled` в API источников.
- Предусмотреть просмотр собранных новостей, истории постов и отдельного поста с его статусом.
- Ошибки сбора, генерации и публикации записывать в логи приложения.
- Учебный API предназначен для локального запуска без авторизации; управление выполняется через Swagger UI.

**Обязательные эндпоинты:**

| Метод | URL | Назначение и ответ |
| --- | --- | --- |
| GET | `/api/sources/` | Список источников, HTTP 200 |
| POST | `/api/sources/` | Создание источника из `type`, `name`, `url`, `enabled`; созданный источник, HTTP 201 |
| GET | `/api/sources/{id}/` | Данные источника, HTTP 200 |
| PATCH | `/api/sources/{id}/` | Изменение переданных полей источника, включая `enabled`; обновлённый источник, HTTP 200 |
| DELETE | `/api/sources/{id}/` | Удаление источника без связанных новостей, HTTP 204 |
| GET | `/api/news/` | Список собранных новостей, HTTP 200 |
| GET | `/api/posts/` | Список постов и их состояний, HTTP 200 |
| GET | `/api/posts/{id}/` | Пост со сгенерированным текстом, статусом и `last_error`, HTTP 200 |
| POST | `/api/parse/` | Без параметров; постановка задачи сбора из всех включённых источников в Celery; `{"task_id": "..."}`, HTTP 202 |
| POST | `/api/generate/` | Тело `{"news_id": "..."}`; создание поста и постановка задачи генерации; `{"post_id": "..."}`, HTTP 202 |
| POST | `/api/posts/{id}/publish/` | Без тела запроса; постановка задачи отправки; `{"post_id": "..."}`, HTTP 202. Если пост уже опубликован — сохранённый пост, HTTP 200 |

- Для неизвестного идентификатора новости, поста или источника возвращать HTTP 404; для некорректных входных данных — HTTP 422.
- Для ручной генерации по новости отключённого источника возвращать HTTP 409 без создания поста и постановки задачи. Для удаления источника со связанными новостями и публикации поста без готового текста также возвращать HTTP 409.
- Ручной запуск сбора, генерации и публикации возвращает ответ после постановки задачи в Celery, не ожидая завершения внешних запросов. Результат сбора виден в `/api/news/`, состояние и результат работы с постом — в `/api/posts/{id}/`.

## 3. **Структура данных**

**Хранение данных и связи:**

- Новости, посты и источники, включая значение `enabled`, хранить в постоянной БД. Данные, история публикаций и готовые посты в очереди должны сохраняться после перезапуска сервиса.
- Рекомендуемая БД — **PostgreSQL**. Окончательный выбор БД остаётся за студентом при выполнении требований к хранению и целостности данных.
- FastAPI и все Celery workers должны работать с одной общей БД. Сохранять изменения так, чтобы они были доступны другим процессам сервиса.
- Каждая новость связана с источником через `NewsItem.source_id → Source.id`, каждый пост — с исходной новостью через `Post.news_id → NewsItem.id`. Обеспечить целостность этих связей; переименование источника не должно нарушать связь с его новостями.
- Удаление источника со связанными новостями запрещено; вместо удаления доступно отключение через `enabled=false`. Новости и посты при отключении сохраняются.

**Модель NewsItem:**

- `id` (uuid)
- `title` (str; непустой заголовок из источника; если его нет — первые 200 символов первой непустой строки `raw_text`, после удаления пробелов по краям строки)
- `url` (str; для сайта — обязательный абсолютный URL статьи; для Telegram — ссылка на исходное сообщение, если доступна, иначе `null`)
- `telegram_channel_id` (int, optional; числовой ID канала-источника, обязателен для Telegram; `null` для сайта)
- `telegram_message_id` (int, optional; ID исходного сообщения внутри канала, обязателен для Telegram; `null` для сайта)
- `summary` (str, optional; сводка, предоставленная источником; если отсутствует или пуста — `null`)
- `source_id` (тип идентификатора `Source.id`; обязательная ссылка на источник)
- `published_at` (datetime, optional; время публикации в источнике, приведённое к UTC; если неизвестно — `null`, не подменять временем сбора)
- `collected_at` (datetime; время сбора новости сервисом, UTC)
- `raw_text` (str; непустой исходный текст новости для сайтов и Telegram; для сайтов — без HTML-разметки)

**Модель Post:**

- `id`
- `news_item_id` (тип идентификатора `NewsItem.id`; обязательная ссылка на исходную новость)
- `generated_text` (str, optional; `null` до успешной генерации, затем — непустой текст поста)
- `generated_at` (datetime, optional; время успешной генерации и постановки в очередь, UTC; `null` до завершения генерации)
- `published_at` (datetime, optional; фактическое время публикации, UTC; `null` до успешной отправки)
- `status` (new/generated/published/generation_failed/publication_failed)

**Состояния Post:**

- `new` — запись создана, успешного результата генерации ещё нет.
- `generated` — текст успешно сгенерирован и ожидает публикации в очереди.
- `published` — пост успешно отправлен в целевой канал.
- `generation_failed` — генерация завершилась ошибкой; `generated_text`, `generated_at` и `published_at` равны `null`.
- `publication_failed` — отправка завершилась ошибкой; готовый текст и время генерации сохранены для повторной отправки, `published_at` равен `null`.
- Основной путь: `new → generated → published`. При повторной генерации после `generation_failed` успешный результат переводит пост в `generated`; при повторной отправке после `publication_failed` успешный результат переводит пост в `published`.

**Модель Source:**

- `id`
- `type` (site/telegram)
- `name`
- `url` (str; для `site` — поддерживаемый адрес страницы сбора новостей или ленты, по которому выбирается парсер; для `telegram` — публичный username или ссылка `https://t.me/<username>`)
- `enabled` (bool; при `false` источник исключён из новых задач сбора и генерации, сохранённые новости и посты остаются в БД; готовые посты продолжают публиковаться по расписанию)
